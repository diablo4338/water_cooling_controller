# Runtime design milestones

This is a record of the design decisions that led to the current implementation. See [runtime behavior](runtime.md) and the [transition reference](state-machines.md) for the executable policy.

| Milestone | Decision and motivation |
| --- | --- |
| State ownership and notification routing | Give each lifecycle one owner. Configuration publishes coherent snapshots, the fan task applies output, and protection controls the output during its adjustment. BLE delivers authorized snapshots and results. Client connection and command identities keep delayed callbacks from changing a newer session |
| Interrupted service operations | Closing the app during calibration had overwritten the previous settings. Keep service output and candidate fields in an operation-local draft. Confirm rotation and the applied command, then commit the permitted fields once. Owner disconnect before commit cancels the operation. An in-progress commit reaches its result |
| Complete configuration commits | Merge changed fields into one candidate, validate it, save one versioned record with the global maximum, and publish the complete RAM snapshot after successful persistence. Serialize saves with a commit mutex. A durable marker allows boot to resume an interrupted factory reset. A revision check prevents an operation started before the reset from writing back stale fields. Profiles remain available after factory reset |
| Thermal sensor failure and recovery | Distinguish ADC I²C failure from a missing control thermistor on a working bus. A failed input clears the overheat state and temporarily selects Always on at runtime. Recovery reactivates the selected temperature mode. A new request to select temperature control needs a valid input. Always on continues to report sensor diagnostics and runs without temperature-based output or overheat decisions |
| Global saved ceiling and RAM-only correction | Make **Maximum output** global, with a factory default of 100%. A manual save can raise or lower it. The protection search cannot raise the preceding confirmed temporary cap. The current effective ceiling is visible, and **Reset overload** clears both the temporary cap and the latched overload when enabled. Reboot discards the temporary cap |
| Settings applied during overload | Reject new Apply, Apply profile, and Save maximum requests while adjustment owns the output. Let a write already admitted finish and then take a fresh configuration snapshot. Explicit service cancellation or disconnect can still send a priority stop |
| Profiles and boundary validation | Resolve bounds on the controller. With saved maximum 70%, a valid incoming base speed of 80% through Apply or 100% through a profile is saved as 70%. Applying a profile preserves the slot and reports the cap or skipped fields. Saving a lower maximum reduces an incompatible base speed in the same write |
| Low-speed tachometer and calibration | Extend the per-channel sample window and accept valid periods for speeds down to approximately 120 RPM with a two-pulse fan. Calibration checks fresh, complete windows after the driver applies and settles at the candidate. It requires consecutive valid windows and verifies rotation again before committing. Displayed RPM alone is insufficient evidence for a calibration result |
| Impulsive loads and shared sampling | The first version used one continuous-low GPIO ALERT qualifier across every overload stage. Give INA226 I²C ownership to one monitor with a 500 ms readiness check and timestamped cache. A failure during ordinary operation leaves the last ceiling in force and raises a visible diagnostic. A failure during correction uses a conservative fallback, with the preceding cap restored on the verified minimum recovery path |
| Different meanings of the base speed | In temperature mode it is the lower end of running demand. In Always on it is the requested percentage. Both operating modes can probe below the saved base. A confirmed temperature-mode cap can reduce both the effective minimum and maximum. The UI says **Base fan speed, %**, and the compatibility field remains `fan_min_speed` |
| Search algorithm revision | A formula followed by a single reduction relied too heavily on an approximately linear load. Three stable samples and then two samples within 5 mA were considered for the formula. The first upward-search version used a post-qualification sample for a quick initial drop, then tried +5 percentage points at intervals of at least 1.5 s, and rolled back 5 points after a qualified alert. It verified the rollback before confirming the ceiling. INA226 averaging remains at the tuned 512 samples |
| Current-only overload protection | An observed case showed 95% output and 119.2 mA at a 100 mA threshold with status OK. The limiter now uses cached INA226 current for initial detection, upward search, rollback and steady-state monitoring. Each step waits for a complete conversion after the applied change. The hardware ALERT function is disabled |
| Zero-output anomaly | A current measurement above threshold over a full averaging window at applied 0% latches a distinct overload-without-load diagnostic. A zero probe with current within threshold can yield a temporary 0% ceiling. An overload alarm uses the LED and buzzer independently of the overheat buzzer setting |
| Notification-based client status | Subscribe to runtime status and read initial snapshots during connection. Later status changes arrive through BLE notifications. The extended output-range characteristic can fall back to the older limit characteristic if absent. Reset sends one command and waits for its sequenced terminal notification. Explicit commands can still read back their results |

The overload journal is the live firmware console. Capture from `firmware/` with `idf.py -p COMx monitor` while reproducing an overload. The `output_limit` tag records the transition reason, measured current, sample sequence, averaging-window start bound, threshold, probe, and applied output.
